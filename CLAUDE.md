# Lorelamp – project rules for coding agents

Local AI roleplay / character-chat app for Windows (desktop window + phone browser or Android app over Wi-Fi). AGPL-3.0, public on GitHub.

## Name
The app is called **Lorelamp** (lore + lamp: stories read by lamplight). Use that name wherever people see it: window title, page title, the wordmark, notifications, log export, user agent `Lorelamp/<version> (+https://github.com/Lampe332/lorelamp)`), README and docs. Never use "Tavern" or "NSFW" in names. The old working title "rp-app" stays in everything a rename would break: crate and binary names `rp-core`, `rp-server`, `rp-desktop`), the data folder `%APPDATA%\rp-app` and every file name in it `rp-app.db`, backups `rp-app-…db`), lock files, the Tauri `identifier` `org.rpapp.spike`; changing it loses the WebView's browser data) and the `rp-` prefixes of localStorage keys. The logo is a flame with an open book in its belly (the book is the light: gold at the book, orange, red-orange at the tips) on a rounded indigo tile. Its masters live in `design/icon/`: `lorelamp-icon.png` (1024 px, corners transparent) plus `lorelamp-icon-foreground.png` (mark and glow inside Android's 66 dp safe circle) and `lorelamp-icon-background.png` (the field to the edges), all three drawn by `build_icon.py` (numpy, opencv-python, scipy; ~1 min, CPU), and `lorelamp-icon-small.svg`, the flat reduced cut for 16-32 px (bigger flame and book, no glow). `design/icon/make_icon.py` (Pillow + the Tauri CLI of `apps/desktop`) renders every icon from them, everything of 32 px or less from the small cut: desktop set incl. `icon.ico` (16-256 px), Android (adaptive icon as foreground/background bitmaps per density, legacy square and round mipmaps, the start page's `ui/lorelamp.svg` + flickering `ui/lorelamp-lit.svg`), favicon `.svg` + `.ico`), manifest icons (incl. maskable) and Apple's touch icon. The app draws the small cut itself `BrandMark` in `apps/web/src/ui.tsx`, in the icon's own colours in every theme: tokens `--mark-*`, set once in the Graphit block); there and on the Android start page the flame flickers (transform only, still with reduced motion), the book never moves; file icons are still.

## Architecture (decided)
- ONE HTTP + WebSocket API in the Rust core `crates/server`, axum) used by both the Tauri window `apps/desktop`) and phone browsers. No separate Tauri IPC path.
- Personas: table `personas` (name, pronouns, appearance, personality, background, description, picture, `every_turn`, `card_priority`); one is active globally, a chat can be bound to one `chats.persona_id`), a character can set a default for new chats `default_persona_id`) and override the priority `user_priority`). The effective persona of a chat is its own ?? the active one; the role/relationship of `{{user}}` always comes from the card.
- Server layout: `crates/server/src/lib.rs` (config, router), `routes/` (handlers per area), `store/` (SQLite by area + `MIGRATIONS` in `store/mod.rs`), `logs/`, `error.rs` `ApiError`), `backup.rs` (database backups via the SQLite backup API in `<data>/backups/`: daily, before migrations, manual, before a restore; retention see Backups below; restore through `Hub::restore_backup`), `guard.rs` (host/origin/token), `reqlog.rs`, `web.rs` (static UI: embedded via feature `embed-ui`, or `--web-dir`), `chat.rs` (Hub). Further crates: `crates/hw` (GPU/driver/WDDM VRAM counters, RAM/commit, backend suggestion), `crates/models` (Hugging Face search/tree, resumable SHA-256-checked download), `crates/core/src/gguf.rs` (GGUF metadata).
- Storage: SQLite via `rusqlite` `crates/server/src/store/`). Schema changes are appended to `MIGRATIONS`; never edit an entry that has shipped. Deleting with undo is a soft delete `deleted_at` on characters, chats, messages) that is purged at the next start.
- Changes to the messages of a chat (edit, rewind, undo, fork) go through `Hub` in `crates/server/src/chat.rs`: refused while the model writes in that chat, then every device gets the chat's new `history` snapshot over its socket.
- Model engine: llama.cpp `llama-server`. Engines and model profiles (model file, load args, sampler, reasoning) live in the database (migration 12; exactly one active profile). The supervisor in `crates/server/src/engine/supervisor.rs` (on with `Config::manage_engine`: the desktop app, `rp-server --manage-engine`) starts the active profile, restarts it after a crash, switches it when the profile's start arguments change (never while a reply is written) and sends `{"type":"engine",…}` to every device; a lock file makes sure only one app instance manages it. A model server the app started always ends with it — closing the window (X) stops it, also while it loads, and a hard end (crash, Task Manager) ends it through a Windows job object with kill-on-close `engine/job.rs`; the old `stop_on_exit` setting is gone); programs started elsewhere are never stopped. Before a start the build's `--help` is read `engine/probe.rs`) and unknown flags are left out. The port is always passed (setting `engine_port`, default 8080, never llama.cpp's 9931; changeable with `PUT /settings {engine_port}`, the model server moves at its next start). After 3 crashes within 5 minutes it gives up for good until the start arguments change, `POST /engine/restart` or an app restart; a port held by another program (not a llama-server) starts nothing and shows as `problem: {code:"port_busy",port}` in `GET /engine` (gave up: `{code:"gave_up",crashes}`); a program on the port is never stopped. The sampler comes from the active profile per request `rp_core::sampler`; defaults temperature 0.8 / n_predict 800). `n_predict` is the answer length, not a cut-off `rp_core::length`): the per-turn tail asks for about 85 % of it in words, at most the length itself, in the chat's language `prompt::length_note`, none above 2048 tokens), a reply is never longer: from 85 % of it `length::MARK_PERCENT`) the reply ends at the first clean sentence end, one with no speech („…“ “…” »…« «…» "…") and no *action*/_thought_ open `SoftStop`, also for "Weiter schreiben", counting its own part and what its base text left open; not with reasoning on), only text up to a sentence end is shown from the mark on, and llama-server gets the length itself as `n_predict` `length::hard_cap`); a reply that reaches it is cut back to the last sentence end since the mark and the open marks are closed `SoftStop::finish`). With reasoning on the old `length::cap` (+50 %, at most +200) stays and there is no soft stop. `%APPDATA%\rp-app\engine.json` is taken over once and otherwise only used when no profile is active.
- UI: React + TypeScript + Vite (React Compiler on) with hand-written CSS `apps/web/src/style.css`), no UI library. Shell/hooks in `src/app/` (Sidebar, useChatSocket with token batching, useEngine, useLibrary, route), side pages are lazy-loaded, long chats are windowed `src/virtual.ts`), server address configurable `api.ts` `apiUrlwsUrl`). Screens: `Hub.tsx` + `src/hub/` (start, five switchable layouts — all five are permanent, do not remove any; shared blocks in `hub/blocks.tsx`; parts used by every layout — model status with one action, first steps, one-click new chat, stars, new imports, on-screen layout switch — in `hub/extras.tsx` + `hub/hub.css`), `src/persona/` (persona switcher, editor, pickers), `Library.tsx` (characters), `Character.tsx` (header with tabs, chat overview, card editor), `Chat.tsx` + `src/chat/` (how a chat looks: `look.ts`, per-chat panel `LookPanel.tsx`, large portrait `Stage.tsx`, fading answer text `Prose.tsx`), `Settings.tsx` (tabs General, Chat = `settings/ChatTab.tsx`, Model + Expert = `src/settings/`, Suggestions + downloads = `src/models/`, Backups, Logs), import page `src/import/`, card export `CardExport.tsx`, picture input `PictureField.tsx` + `image.ts`, `Persona.tsx` (switcher, phone sheet, persona manager, chat/character persona pickers), `UserFit.tsx` (character settings: what the card says about the user), `Palette.tsx` + `search.ts` + `spot.ts` (Ctrl+K and the command field: local fuzzy search that also finds settings and opens the exact spot). ## Rules
1. Real implementations only — no mocks, stubs or TODO placeholders as a substitute. If a dependency is missing: stop and ask.
2. After every change to the app: rebuild the web UI and the release EXE (the owner starts the app via a desktop shortcut to `target/release/rp-desktop.exe`). A running instance locks the file — ask the owner before closing it, and close it normally (close the window), never kill it. From the Claude desktop shell a close message does not reach the app started via Explorer: run `(Get-Process rp-desktop).CloseMainWindow()` from a `.cmd` started with `Start-Process explorer.exe '"<path>\close.cmd"'`. Before a build that adds a migration, back up the owner's `rp-app.db`. Then do a one-click test. Since R1 the UI is embedded into the EXE at compile time `apps/web/dist` must be built before `cargo build`); an EXE built before R1 still reads `dist` from disk, so until the owner's EXE is rebuilt do not run `npm run build` while it is open. Release builds take ~2 min (thin LTO, codegen-units 1).
3. One-click test = start the shortcut the way a double-click does: `Start-Process explorer.exe '"<path>\Lorelamp.lnk"'`. The shortcut `Lorelamp.lnk` → `target\release\rp-desktop.exe`, Lorelamp's icon) is made by `scripts\make-shortcut.ps1` `-RemoveOld` deletes the old `RP-App.lnk`, `-ResetNameCache` makes Windows read the name "Lorelamp" from the EXE again, e.g. in the firewall prompt). A process started directly from an agent shell can see a redirected `%APPDATA%` and therefore different settings and data than the owner's real app.
4. Never `git push`, create a GitHub repo or release without the owner's explicit go right before it. Commit only when asked. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
5. No personal data in the repo: no user paths, model paths, chats or character cards. Personal settings and data live only in `%APPDATA%\rp-app\`.
6. GPU safety: VRAM is limited (24 GB on the dev machine) — never start a second model server next to a running one. **Never start the Vulkan backend without asking** (a Vulkan benchmark crashed the dev PC with screen artifacts). Stop every process you started.
7. Measure performance through `llama-server` timings, not `llama-bench` (wrong numbers for iSWA models). VRAM: on Windows+HIP the free value from llama.cpp `--list-devices`, and therefore `--fit`) never changes and is useless; real usage comes from the WDDM counters `crates/hw`: adapter dedicated/shared, per-process shared = overflow into system RAM, minus pinned host buffers of CPU-offloaded experts). See `docs/benchmarks.md` M0.
8. Prompt building must follow layout B from `docs/cache.md`: static head (system, card, examples), history that only grows at the end, all per-turn content (post-history instructions, notes) appended to the final user message.
