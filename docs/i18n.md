# Translating the UI

Lorelamp's UI is written in German and shown in German, English, Spanish or Russian. The language is
a server setting (`PUT /api/settings {language}`, chosen in Settings → Allgemein → Sprache): every
connected device shows it, and the figures answer in it from the next reply on (`crates/core/src/prompt.rs`,
`Language`).

The scaffold lives in `apps/web/src/i18n/`. The app frame has the dictionaries `shell` (sidebar,
phone bars and "Mehr", tablet rail, Ctrl+K, settings head, Settings → Allgemein, toasts, the
server's error codes) and `commands` (the quick actions). Every other screen belongs to one of the
four areas below, each with dictionaries of its own, so changes in different areas never touch the
same files.

## How a text is translated

1. **German is the source.** Each area has one dictionary file per language:
   `src/i18n/dict/<area>.de.ts` (the keys and the German text), `<area>.en.ts`, `.es.ts`, `.ru.ts`.
   Keys start with the area's name (`chat.`, `cards.`, `models.`, `system.`), so two areas never
   share a key. Name a key after its place and job: `chat.look.title`, `chat.look.title.note`,
   `models.bench.run`. A wrong key, or a `{place}` without its value, does not compile.
2. **Use it:** `import { t } from "../i18n"` and write `t("chat.look.title")` where the text was.
   Values go in by name: `"Chat mit {name}"` → `t("shell.nav.chatWith", { name })`.
3. **Never call `t()` at the top level of a module** (the text would stay in the language the app
   started in). A table of texts there becomes a function (`const rows = () => [[id, t(…)], …]`) or
   uses `texts()`: `texts({ id: "poster" }, { name: "cards.layout.poster" })` gives a row whose
   `name` is read in the language on screen each time (never spread such a row).
4. **Text with markup in it** (a link, `<code>`, `<b>` in the middle of a sentence): `rich()` from
   `src/i18n/rich.tsx` puts each node at its `{place}`, so each language keeps its own word order:
   `rich("shell.general.persona.macro", { macro: <code>{"{{user}}"}</code>, name })`.
   Never glue a sentence together from pieces.
5. **Counts** use plural forms, picked by `Intl.PluralRules`:
   `"chat.hits": { one: "{n} Treffer", other: "{n} Treffer" }` → `t("chat.hits", { n })`.
   German, English and Spanish need `one` and `other`; Russian needs `one` (1, 21 …), `few`
   (2–4, 22–24 …), `many` (0, 5–20 …) and `other`. A form left out falls back to `other`.
6. **Numbers, dates, sizes** come from `Intl` in the app's language: `num(n)`, `numberFormat(opts)`,
   `dateFormat(opts)` from `src/i18n`. `{n}` and other number values are formatted by `t()` itself;
   pass a port, an id or a year as a string so it is not written as "8.080".
7. **Server error codes** are `shell.err.<code>` (70 of them, in `shell`); `errorText(e)` in `api.ts`
   reads them. Do not write error texts of your own for a code. A code without a text: leave it,
   name it in your return; the main chat adds it to `shell` after the merge.
8. **A translation file** starts as `Partly<typeof chatDe>` (a gap shows the German text) and becomes
   `Fully<typeof chatDe>` once the area is done, so a later German key without a translation fails
   `tsc`. A group is done when all four files of its area are `Fully` (German is the source).
9. **What is not translated:** log texts (`logEvent(...)`, `data-log-label`; the log is a record for
   the owner, never shown as the UI's words), ids and values sent to the server, the names in
   `LANGS` (each language under its own name), proper names (Lorelamp, SillyTavern, Hugging Face,
   …), and everything the user wrote (cards, chats, persona texts).
10. **Words:** short and plain, like the German. Keep the app's terms in each language: en
    "character / persona / model / chat"; es "personaje / persona / modelo / chat"; ru
    "персонаж / персона / модель / чат". Read `shell.*.ts` of the language before writing new texts.
    Translate only text that appears in the interface.

## The test for German leftovers

`apps/web/e2e/leftovers.ts` makes one test per screen and language (en, es, ru): it sets the
language, opens the screen, reads every visible text plus `aria-label`, `title`, `placeholder`,
`alt` and the options of visible lists, and fails with each German word it finds (fixed rules in
`e2e/german.ts`: letters only German has, and frequent words of the app's German texts). Names of
the test data's characters and personas are left out; parts that hold the user's own text are left
out with `skip` (CSS selectors); further proper names with `keep`. The language is set back to German
after each language's tests.

The frame's table is `e2e/i18n-shell.spec.ts`. A group adds **its own** `e2e/i18n-<area>.spec.ts`
with its screens, e.g.:

```ts
import { leftoverTests } from "./leftovers";

leftoverTests("chat", [
  { name: "Chat", form: "desktop", hash: `/chat/${id}`, region: (page) => page.locator("main"), skip: [".msg-text"] },
  { name: "Chat", form: "phone", hash: `/chat/${id}`, region: (page) => page.locator("main"), skip: [".msg-text"] },
]);
```

`form` is `desktop`, `phone` or `tablet` (1280 × 800 with touch); the tests run in the graphit
projects only. Run your own spec plus the existing specs of your area, never the whole suite.

## The areas

Every UI file with text belongs to exactly one area. Work on an area touches only the files on its
list, its own four dictionary files and its own `e2e/i18n-<area>.spec.ts`; German found in a file
of another area is fixed there, in a change of its own. The tutorial (`tutorial.*`) and the card
builder (`builder.*`) have dictionaries of their own as well.

**Shared, edited by no group:** `src/i18n/` outside the group's own dictionary files (the index
already imports all four areas), the `shell` and `commands` dictionaries, `e2e/german.ts`,
`e2e/leftovers.ts`, `style.css` (a longer text that breaks a layout is fixed in the area's own CSS
file), `commands.ts`, `search.ts`, `spot.ts`.
